# Provenance Policy

`referytale` では、文章に含まれる具体情報と目立つ語彙について「どこから来たか」を確認する。

目的は証拠管理そのものではない。  
**AIが文章を滑らかにするために、材料を勝手に増やすことを防ぐ**ための確認手順である。

## 1. 情報の出所

文章へ入れてよい具体情報は、原則として次のいずれかへ遡れるものとする。

| 区分 | 例 | 扱い |
|---|---|---|
| User | ユーザーが話した経験・意見・事実 | その範囲で利用可 |
| Project | 人物・ブランド・プロジェクトSkillの設定・表現規則 | 適用範囲内で利用可 |
| Source | ユーザー提供資料、一次資料、確認済み情報 | 出典の確度を保って利用 |
| Creative | 明示されたフィクション・仮想例 | 創作範囲内で利用 |
| Unknown | どこにも根拠がない | 非フィクション本文へ追加しない |

「ユーザーならきっとこう思ったはず」はUserではない。Unknownである。

固有Skillの一人称、口調、語彙、リズム、構成は表現規則として利用できる。ただし、非フィクションで人物が実際に何をしたか、何を言ったか、何を感じたかは、固有Skillまたは今回の材料に根拠がなければProjectとして扱わない。

第三者の資料、調査、発言に基づく内容では、誰または何に基づく情報かも意味の一部である。資料に帰属させた記述を、出所のない直接の事実へ変えない。

## 2. 重点確認する情報

AIがもっともらしく補完しやすいため、次を重点的に確認する。

- 場所
- 日時
- 数値
- 発言
- 誰が何をしたか
- 感情
- 動機
- 原因
- 結果
- 回数
- 順序
- 助言・対処方法
- 数値に対する程度の評価
- 否定される内容と、対比の両側にある前提
- 読者を安心させるための断定や助言
- 主語、対象範囲、回数を表す語
- 省略後も中心的な出来事を特定できるか
- 似た述語を持つ別対象を統合し、一方の内容を落としていないか

確認対象は文章の意味内容である。語順、語尾、リズム、間、改行などの文体表現に、素材との完全一致は求めない。出所確認を理由に、固有Skill由来の声を平均的な文体へ戻さない。

「〜ではない」「〜とは限らない」「〜だけで決まらない」のように否定しても、否定対象を新たな話題として持ち込んだことに変わりはない。否定文では否定される内容を、対比文では対比の両側を分けて照合する。

「その」「これら」などの指示語も参照関係を加えることがある。独立して並ぶ内容をつなぐ際、材料にない参照先や因果を補わず、対象が省かれている語は省かれたまま保つ。

本人の経験は、その本人についての材料である。読者層が指定されても、「新人」「利用者」「誰でも」にも成り立つ主張の出所にはならない。また、「予定があった」とだけ分かる場合、予定の具体的内容はUnknownのまま扱う。

## 3. 意見の強度

ユーザーの意見を読みやすく言い換えることはできるが、強度を勝手に弱めたり強めたりしない。

- 「少し違和感がある」→「間違っている」にしない
- 「かもしれない」→「〜である」にしない
- 「私はこう感じる」→「一般に〜だ」にしない

数値を「高い」「大きい」「顕著」「十分」「わずか」などと評価する場合は、その基準または同じ表現が資料にあるか確認する。基準がなければ数値をそのまま示し、程度を表す評価語を補わない。

## 4. 語彙の出所

目立つ概念語、独自表現、タイトルの核になる語は、次のどれかへ分類する。

| 区分 | 扱い |
|---|---|
| User term | 原則維持。一般語でないことだけを理由に削らない |
| Project term | 定義された意味と適用範囲を守る |
| Source term | 引用・参照元の意味を変えない |
| Established term | 一般的な意味で使う |
| Model-coined | 命名依頼でない限り採用しない |

確立語か判断できず検索可能なら確認する。確認できない場合は、普通の説明へ戻す。

タイトルと見出しも独立した意味内容として照合する。本文中の個人的な経験や「かもしれない」を、主語の広い断定へ変えたタイトルは採用しない。

命名依頼では、候補ごとに名称を外した一文の定義を作る。各定義がそれぞれ単独で、依頼元の主体、動作、原因、時間関係、結果をすべて保つか確認する。別候補の定義で不足を補わず、一つでも欠ける候補は作り直す。

## 5. 初稿の出所照合

根拠となるメモ・資料と初稿が分かれている場合、初稿は事実内容の出所ではない。読みやすく書けていても、初稿そのものを根拠にして内容を残さず、メモ、固有Skill、参照資料、明示された創作設定へ戻って照合する。初稿の言い回しは、ユーザーが残すよう求めた場合に表現上の材料として使える。

別の根拠資料がなく、ユーザー自身の原文を通常のリライトとして渡された場合は、その原文をUser由来の材料として扱う。原文の内容まで一律にUnknownへ落とさない。ただし、ユーザーが未確認の下書きだと明示した箇所は、確認済みの事実へ格上げしない。

通常の文章では、次の表を内部で使う。

| 初稿の意味内容 | 種類 | 遡れる材料 | 判定 |
|---|---|---|---|
| 事実・経験・行動・感情・原因・評価・助言・語彙など | 種類を一つずつ記載 | User / Project / Source / Creative / Unknown | 使用 / 削除 / 未確認と明示 |

- 一文に複数の意味内容がある場合は分ける。
- 「記事として自然」「人物らしい」「読者に役立つ」は、`遡れる材料`へ書かない。
- `Unknown`は、ぼかして残すのではなく削除する。依頼上必要な推測だけは、推測と明示して残せる。
- 削除後は、使用できる内容と固有Skill由来の表現規則だけでつなぎ直す。
- つなぎ直した文章をもう一度照合する。
- 2回目でも`Unknown`が残る場合は初稿を破棄し、使用できる材料を意味の変わらない言い方で並べた短い文章へ戻す。
- 削除後に、材料の中心的な主体、出来事、順序、因果、不確実性が完成稿だけでも判別できるか確認する。
- 材料側から完成稿へも一項目ずつ逆照合し、対象や範囲が違う項目を一つへまとめて欠落させていないか確認する。

別の検証担当を利用でき、今回の権限と作業範囲内で完結する場合は、重要な非フィクションや同じ失敗が繰り返された文章の照合を分離してよい。その担当へ渡すのは、使用可能な材料、固有Skillの表現規則、初稿である。初稿を作った理由や意図は渡さず、初稿を正当化する材料にしない。検証担当は新しい具体例や改善案を足さない。

## 6. Provenance Table モード

通常の短文では対応表を必須にしない。

ただし、次の場合は **Provenance Table** を作る。

- ユーザーが「厳密に」「根拠を追えるように」「出所を確認して」と求めた
- 対外文書、重要な非フィクション、長文
- 複数資料や複数の固有Skillをまたぐ
- 独自表現、専門語、未確認事項が多い

この表の目的は、新しい名称を割り当てることではない。  
**本文に使う事実・経験・意見・語彙が、どの材料へ遡れるかを外部化すること**である。

```markdown
| ID | 内容 | 種類 | 出所区分 | 出所の識別子・箇所 | 確度 | 本文での扱い |
|---|---|---|---|---|---|---|
| P1 | 週2回出社している | 事実 | User | 依頼文「週2回出社している」 | confirmed | 使用可 |
| P2 | 出社がつらい理由は睡眠不足 | 原因 | Unknown | 該当なし | unknown | 削除 |
| P3 | 「他責力」 | 語彙 | User term | 依頼文「『他責力』と呼びたい」 | confirmed | 維持 |
```

`ID` は追跡用であり、意味を持つ概念名にしない。

`出所区分`だけでなく、該当箇所へ戻れる識別子を記録する。ユーザー入力なら該当文、ファイルなら相対パスと見出しまたは段落、Web資料ならURLと節、固有SkillならSkill名・ファイル・規則の見出しを使う。「資料A」「確認済み情報」のように元の記述を特定できない書き方で済ませない。

### 表を作るタイミング

原則として本文の前に主要材料を登録する。

執筆中に新しい具体情報や独自表現が必要になった場合は、本文へ先に足して後から正当化せず、出所を確認して表へ追加してから使う。

### ファイルへ保存する場合

Provenance Tableは、作業環境がファイルを扱える場合も原則として内部で使い、ファイルを残さない。ユーザーが表のファイル保存を明示的に求めた場合だけ、次へ保存する。

```text
<work-root>/.codex/provenance-tables/provenance-table-<slug>.md
```

- Gitリポジトリではリポジトリルートを `<work-root>` とする。
- Gitリポジトリでない場合は、対象文書を保存する作業フォルダを `<work-root>` とする。複数の対象文書がある場合は、依頼で作業対象になっている共通フォルダを使い、ドライブ直下やホーム全体のような広い場所へ置かない。
- `<slug>` は対象を識別できる短いkebab-caseにする。
- 保存した表は本文の一部ではなく、確認用の作業成果物として扱う。
- 保存できない会話環境では、内部の作業表として同じ列を使えばよい。

Gitリポジトリへ保存する場合は、保存前に、保存予定のパスが利用先リポジトリの除外設定で無視されることを確認する。無視されない場合は、ユーザーが `.gitignore` の変更を明示的に許可していない限りファイルへ保存せず、内部の作業表として扱う。`.gitignore` を無断で編集しない。

ユーザーが表のファイル保存を求め、かつ `.gitignore` の変更を許可した場合は、次の設定を利用先リポジトリへ追加してから保存してよい。

```gitignore
# Temporary ReferyTale provenance artifacts
.codex/provenance-tables/
```

### 表に載せるもの

すべての一般語を記録する必要はない。次を優先する。

- 個人的な経験・出来事
- 数値・日時・場所・発言
- 原因や動機
- ユーザーの意見・解釈
- 人物・ブランドSkill由来の設定
- タイトルや論旨の核になる独自表現
- 一般語か判断に迷う概念語
- 未確認のまま残す必要がある内容

### 完了条件

- 本文の主要な具体情報が表へ遡れる
- AI独自の名称が紛れ込んでいない
- Unknownを断定へ変えていない
- Project term / User term の意味を勝手に拡張していない
- 遡れない具体情報を削除し、残った材料だけで文章をつなぎ直している

## 7. 素材不足時

素材が足りないときにやってはいけないこと。

- 具体例を発明する
- セリフを作る
- 原因を決める
- 心理状態を診断する
- 一般論で文字数を埋める
- 新しい概念名を作って説明した気になる

代わりに、抽象度を保つ、未確認として残す、追加材料を求める、確認可能な事実だけ調べる、のいずれかを選ぶ。
