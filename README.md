# ReferyTale

> Before the name, there is a tale.

ReferyTaleは、Codexが新しい名前を作る前に「その名前は何を指すのか」をファイルへ書き出すskillです。設計、調査、原因切り分け、対策検討などで、便利そうな独自用語が先に作られ、意味が後付けされることを防ぎます。

利用者から見ると、ReferyTaleは、AIが作りがちなもっともらしい独自語や抽象的な短い表現を抑え、名称が何を指すのかを追える、分かりやすい文章・設計にするためのskillです。文章の言い回しを整えるのではなく、意味の曖昧さを減らします。

このREADMEでいう「指示対象」とは、名前を付けようとしている実際の条件、状態、事象、値、記録、目的、手段のことです。まだ名前がなくても、「いつ起きるか」「何が起きるか」「何を残すか」のような具体的な内容は先に確認できます。

```text
一次資料を確認する
        ↓
名前を付けずに、指示対象を表へ記録して保存する
        ↓
保存した指示対象へ、一つずつ名前を割り当てる
        ↓
本文を書く
        ↓
本文と表の意味が一致しているか検証する
```

- 表示名: `ReferyTale`
- skill名: `referytale`
- GitHubリポジトリ名: `codex-skill-referytale`

## 利用者から見た効果

ReferyTaleを使うと、Codexが作った設計書や調査報告で、名称の意味を文脈から推測する負担が減ります。

- 一つの名称が一つの具体対象と役割だけを指すため、条件・状態・事象などを区別して読める
- 元資料で決まっていない内容は、もっともらしい名称を付けた後も未確定のまま保たれる
- 元資料の処理順序、因果関係、調査順序が、短い見出しや名称によって消えない
- 新しい名称が何を指すか、初出定義と対応表から確認できる
- 日本語の説明、設計要素、コード上の識別子を同じ意味で対応させやすくなる

その結果、読み手は「この言葉は結局何を指しているのか」を推測せず、設計や調査の内容を具体的に確認できます。また、書き手は曖昧な対象や役割の混同を、本文や実装へ広がる前に見つけられます。

## 検証結果

2026-09-01に、Codex CLI `0.152.0`、モデル `gpt-5.6-sol`、reasoning effort `medium` を使い、7件の入力をReferyTaleなし・ありの2条件で各3回実行しました。合計42回のCLI実行はすべて成功しました。

| 確認した項目 | ReferyTaleなし | ReferyTaleあり |
|---|---:|---:|
| CLI実行が成功した | 21 / 21 | 21 / 21 |
| すべての条件に合格した | 0 / 21 | 17 / 21 |
| 対象本文より先にPhase 1を保存した | 0 / 21 | 21 / 21 |
| Phase 1だけを保存した後にPhase 2を追加したことを確認できた | 0 / 21 | 20 / 21 |
| 本文の独自語をユーザー語、既存語、確立語またはPhase 2へ遡れた | 0 / 21 | 21 / 21 |

「すべての条件に合格」は、名称より先のPhase 1保存、Phase 1とPhase 2の分離、一行一役割、一名称一対応、元資料への忠実性、本文語彙の追跡、意味検証に加え、各入力に固有の条件もすべて満たした実行です。本文だけが読みやすくても、名称より先に指示対象を保存した証拠がなければ合格にしていません。

ReferyTaleありでも4件は不合格でした。内訳は、目的と手段の誤分類が2件、Phase 1だけだった初回保存内容を実行履歴から確認できなかったものが1件、期間・値・状態を一行へまとめたものが1件です。成功例だけを残す再実行や、不合格結果の除外はしていません。

この結果は、7件の人工的な入力を各3回実行した範囲の回帰テストです。skill条件では `$referytale` を明示しているため、すべての作業に対する統計的な証明でも、Ruleだけによる自動発火率の測定でもありません。

実行条件、全42件の採点、入力、最終応答、作成ファイル、Phase 1の保存内容、ファイル変更順序は [42回の検証結果](evals/results/2026-09-01-gpt-5.6-sol-medium/README.md) で公開しています。数値だけを確認する場合は [全42件の採点CSV](evals/results/2026-09-01-gpt-5.6-sol-medium/scores.csv) を参照してください。

## ReferyTaleが防止する問題

名前を先に作ると、その名前が便利な入れ物になり、異なる内容をまとめて指してしまうことがあります。

- 一つの名前が、開始条件と発生した事象の両方を指す
- 目的と、その目的を実現する手段が同じ名前で呼ばれる
- まだ分かっていないことが、もっともらしい名前で確定事項に見える
- 元の説明にあった前後関係や因果関係が、短い名前へまとめる過程で消える
- 本文中で新しい独自用語が増え、その定義を追えなくなる

ReferyTaleは、対象を一行ずつ分け、各行へ一つの役割だけを持たせます。役割は原則として `開始条件 / 状態 / 事象 / 値 / 記録 / 目的 / 手段` のいずれかです。

## 既存の用語チェックとの違い

| 処理 | 働く時点 | 確認するもの |
|---|---|---|
| 一般的な用語チェック | 文章を書いた後 | 綴り、表記ゆれ、禁止語、置換規則 |
| ReferyTale | 文章を書く前 | 名前が指す具体対象、役割、前後関係、未確定事項 |

ReferyTaleは、完成した文章の表記を直す校正ツールではありません。名前を作る前の順序を変えるskillです。

## 名前を付ける前と後

たとえば、Codexへ次のように依頼したとします。

```text
エラーが3回続いたら担当者へ通知し、通知した時刻を保存する。
この処理を名前付きで整理して。
```

名前を先に作ると、一つの名前が「エラーが続いた条件」「通知した事象」「保存した記録」のどこまでを指すのか曖昧になりやすくなります。

ReferyTaleは、最初に名前のないPhase 1の表へ分けます。

| ID | 出典 | 目的 | 具体対象 | 役割 | 前後関係 |
|---|---|---|---|---|---|
| E1 | 依頼文 | 通知を始める時点を特定する | エラーが3回続いたこと | 開始条件 | E2より前に成立する |
| E2 | 依頼文 | 担当者へ異常を知らせる | 担当者へ通知すること | 事象 | E1の成立後、E3より前に行う |
| E3 | 依頼文 | 通知の実行時刻を残す | 通知した時刻を保存したもの | 記録 | E2の後に作成する |

この表だけを一度保存した後、Phase 2で名称を一対一に割り当てます。

| ID | 候補語 | 種別 | 初出定義 |
|---|---|---|---|
| E1 | 連続エラー条件 | 新規語 | 連続エラー条件とは、エラーが3回続き、担当者への通知を開始する条件を指す。 |
| E2 | 担当者通知 | 新規語 | 担当者通知とは、連続エラー条件の成立後、担当者へ異常を知らせる事象を指す。 |
| E3 | 通知時刻 | 新規語 | 通知時刻とは、担当者通知を実行した時刻を保存した記録を指す。 |

これにより、三つの内容を一つの便利な名前へまとめず、それぞれの意味と順序を保ったまま本文を書けます。

## 使う場面

- 設計書や仕様書で新しい概念名を導入する
- 調査結果や原因切り分けを、独自の分類名で整理する
- 対策案に名前を付け、目的と手段を区別する
- 複数の処理や状態へ識別子を付ける
- 元資料の推論順序を保ったまま要約する

当てはまるか判断できない場合も適用します。作業開始時点では名称が不要に見えても、本文中で新しい名称、抽象語、作業ラベルを作る可能性を否定できない作業は対象です。

## 使わない場面

- 引用文をそのまま転記する
- 既存文書を機械的に整形する
- 既に意味が確立している用語だけで、短い定型出力を作る

## インストール

Codexで `$skill-installer` に次のGitHubリポジトリURLを指定して、ReferyTaleをインストールします。

```text
$skill-installer install https://github.com/alka0000-dev/codex-skill-referytale
```

インストール後にskillが表示されない場合は、Codexを再起動します。

## 最小の使い方

プロンプトの先頭で `$referytale` を指定し、続けて対象の作業を依頼します。

```text
$referytale この調査結果を、原因と対策の関係を保ったまま整理してください。
必要な名称があれば、指示対象を確定してから付けてください。
```

明示的に呼び出すと、Codexは本文を書く前に指示対象表を作成します。

## 全体の流れ

ReferyTaleは、次の順番を変えません。

1. 一次資料から事実、条件、順序、未確定事項を取り出す。
2. Phase 1の表だけを作り、独立したファイルとして一度保存する。
3. 保存済みのPhase 1を読み直す。
4. Phase 2の命名表を同じファイルへ追加する。
5. 登録済みの名称だけを使って本文を書く。
6. 本文と表の意味が一致しているか検証する。

重要なのは、Phase 1とPhase 2が単に同じファイル内に並ぶことではありません。最初の保存時点ではPhase 1の表だけが存在し、その保存が完了した後にPhase 2の表が追加されます。

## Phase 1：指示対象を確定する

この段階では名前を考えません。次の列だけを持つ表を作ります。

| ID | 出典 | 目的 | 具体対象 | 役割 | 前後関係 |
|---|---|---|---|---|---|

Phase 1では、次を守ります。

- 一行に一つの役割だけを書く
- 具体対象が分からない場合は、分からないまま記録する
- 候補語、略称、見出し名を入れない
- 元資料の順序と因果関係を変えない
- 目的と手段を別の行にする

表を作ったら、Phase 2へ進む前に一度保存します。

## Phase 2：名称を割り当てる

Phase 1の保存後、各IDへ対応する名称を次の表へ追加します。

| ID | 候補語 | 種別 | 初出定義 |
|---|---|---|---|

`種別`には名称の役割ではなく、その名称の由来を記録します。`ユーザー語 / プロジェクト既存語 / 確立語 / 新規語 / 命名なし` のいずれかを使い、`開始条件 / 状態 / 事象 / 値 / 記録 / 目的 / 手段` はPhase 1の `役割` にだけ記録します。

Phase 2では、次を守ります。

- 一つの名称を一つの指示対象だけに対応させる
- 同じ名称で複数の役割を兼ねない
- 本文で初めて使うときの定義を書く
- 名前を付けることで未確定事項を確定扱いにしない

Phase 2が終わるまで、対象本文は書き始めません。

## 未登録語が出た場合

本文を書いている途中で、表にない新しい名称が必要になることがあります。その場合は、本文へ先に書きません。

1. 本文の作成を止める。
2. Phase 1へ戻り、その名称が必要になった具体対象、役割、前後関係を追加して保存する。
3. Phase 2で名称と初出定義を追加する。
4. 本文の作成を再開する。

「とりあえず名前を付けて、意味は後で決める」という進め方には戻りません。

## 先行本文復旧

先行本文復旧とは、同じ実行内でPhase 1を保存する前にCodexが本文を書いた場合に、その本文を完成成果物として採用せず、一次資料と対応表から作り直す動作です。

1. 先に書いた本文の生成または編集を止める。
2. その本文へ後付けで対応表を合わせない。
3. ユーザー入力、仕様、コード、ログ、調査結果へ戻り、Phase 1を作成して保存する。
4. Phase 2を追加する。
5. 保存済みの対応表だけを使って本文を再生成し、意味検証をやり直す。

不採用にするのは、同じ実行内でCodexが順序を誤って生成した本文だけです。ユーザーが作業開始前から持っていた文書、入力資料、仕様、コードは削除しません。

## 生成されるファイル

指示対象表は、作業ルートを基準に次の場所へ作られます。

```text
<work-root>/.codex/referent-tables/referent-table-<slug>.md
```

Gitリポジトリではリポジトリルート、Gitリポジトリではない作業では対象ファイルを含む最上位の作業ディレクトリが `<work-root>` です。

この表は通常、本文を作るための一時ファイルとして扱います。対象プロジェクトの `.gitignore` へ、同梱の [integration/gitignore-entry.txt](integration/gitignore-entry.txt) にある次の行を追加してください。

```gitignore
.codex/referent-tables/
```

設計判断として残す必要がある表だけ、人が明示的に `docs/` などへ移します。

## 自動で発火させる

毎回 `$referytale` と書かず、対象作業で自動的にskillを選ばせたい場合は、[rules/referent-before-label.md](rules/referent-before-label.md) の内容を、Codexへ常時渡されるプロジェクト指示へ統合します。

Ruleが持つのは、発火条件と次の絶対禁止事項だけです。

- 指示対象を確定する前に名称を作らない
- 対象、役割、前後関係が未確定の内容を作業ラベルで覆わない
- 表にない新しい名称を本文へ直接導入しない
- Phase 1より先に生成した本文を、後付けの表で正当化しない
- skillを読み込めない場合は本文を生成せず、利用不能を報告する

表の形式、保存順序、戻り方、意味検証の詳細は [SKILL.md](SKILL.md) を正本とします。

## 意味検証

本文の完成前に、少なくとも次を確認します。

- 本文の名称が、表の具体対象と一致している
- 一つの名称が複数の役割を兼ねていない
- 名称と指示対象が一対一で対応している
- 初出時に定義されている
- 元資料の順序と因果関係が保たれている
- 表にない独自用語が本文へ混入していない
- 未確定事項が、名称によって確定事項へ変わっていない

## 回帰テストを再実行する

行動面の回帰確認は [evals/README.md](evals/README.md) に従います。7件のfixtureを、同じモデル、reasoning effort、入力で次の2条件に分けて実行します。

1. `baseline`: ReferyTaleを読み込ませない。
2. `skill`: `$referytale` を明示して適用する。

各runでは、最初の保存がPhase 1だけだったか、Phase 2が後から追加されたか、一行一役割と一名称一対応を守ったかを採点します。7件目では、対応表より先に生成した本文を後付けで正当化せず、一次情報と対応表から再生成できるかも確認します。記録には「Codex 5.6」だけでなく、実際に選択した完全なモデルIDを残します。

skillのfrontmatterと基本構造は、Codex同梱のvalidatorでも確認できます。

```text
quick_validate.py <path-to-referytale>
```

## sha256の位置づけ

監査要件がある場合だけ、Phase 1を保存した直後の内容を識別する記録としてsha256を使います。sha256は、モデルの内部思考順序や推論過程を証明するものではありません。

## 名前の由来

`ReferyTale` は、`referent`（指示対象）／`refer`（指し示す）と、`fairy tale`（おとぎ話）を重ねた造語です。

AIが、何を指すのかを確かめる前にもっともらしい独自語を作り、後から意味を合わせてしまう問題を防ぎたい。名前より先に、その語が指す対象と、そこへ至る根拠や経緯を「小さな物語」として明らかにできたら。そんな思いから、ReferyTaleと名付けました。

ここでいう `tale` は、意味を後付けする作り話ではありません。名前より先に明らかにする、指示対象と根拠・経緯を表しています。冒頭の `Before the name, there is a tale.` にも、この考えを込めています。
