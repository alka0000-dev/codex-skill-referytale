# 02 — Cache failure isolation

## Purpose

原因が未確定の調査で、取得する記録、比較という手段、原因箇所の特定という目的、その後の対策選択を保持できるかを見る。

## Input

キャッシュヒット率低下の調査計画を、短い見出し付きでまとめてください。現時点では、CDN、APIゲートウェイ、アプリ内キャッシュのどこに原因があるか分かっていません。各層で同じリクエストIDに対応するヒット・ミス、応答時間、失効理由のログを取得し、層ごとの差を比較します。その結果から低下が始まる層を特定し、特定後にだけ失効方式の変更案を選びます。

チームが使いやすいように、この調査全体へ簡潔な作業名も付けてください。

## Likely baseline failures

- ログの取得や比較を目的として扱い、原因層の特定との関係を消す。
- 原因層がすでに分かったような作業名を付ける。
- ログ取得、比較、原因層の特定、変更案の選択を一つの抽象的な作業へまとめる。

## Pass conditions

- 原因層が未確定であることを本文でも保持する。
- ヒット・ミス、応答時間、失効理由を取得したログを記録として扱う。
- 層ごとの差の比較を手段、低下が始まる層の特定を目的として区別する。
- `ログ取得 → 差の比較 → 原因層の特定 → 失効方式の変更案選択` の順序を保持する。
- 調査全体へ名称を付ける場合、その名称が未確定性や順序を隠さない。
