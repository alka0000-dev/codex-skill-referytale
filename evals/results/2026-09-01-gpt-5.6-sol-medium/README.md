# ReferyTale 42-run regression result

ReferyTaleを適用しない `baseline` と、`$referytale` を明示して適用する `skill` を、7件のfixtureでそれぞれ3回ずつ比較しました。合計42回はすべて独立した空の作業領域で実行し、CLIまたはモデルの実行失敗は0件でした。

厳格な合格条件では、baselineが `0 / 21`、skillが `17 / 21` でした。ReferyTale適用時は、対象本文より先に指示対象を外部化する順序を `21 / 21` で守り、Phase 1とPhase 2の分離を実行履歴から `20 / 21` で確認できました。

この結果は「ReferyTaleが常に完全な文章を作る」という証明ではありません。今回の7題において、独自語を作る前のsemantic preflightを大きく安定させた一方、4件の不合格も残った、という回帰テスト結果です。

## 採点方法

- G1とG2は、ファイル変更順、Phase 1だけを読み返した出力、Phase 2追加後の最終ファイルを実行履歴から確認しました。
- G3〜G7とfixture固有条件は、最終文書、最終対応表、保存途中のPhase 1、実行履歴を人が照合しました。
- G1またはG2が0、G3〜G7のいずれかが0、fixture固有条件が0のどれか一つでも該当すれば、そのrunは不合格です。
- `sha256` はskillとプロジェクト指示の同一性、および成果物監査のために記録しています。モデル内部の思考順序を証明するものではありません。

機械抽出した全runの確認値は [automatic-checks.json](automatic-checks.json) にあります。各fixture配下には、入力、最終応答、最終ワークスペース、Phase 1スナップショット、順序だけに絞ったイベント記録を保存しています。端末固有の絶対パスを含む生のJSONLは公開用成果物へ含めず、採点に必要な情報だけを相対パスへ変換しました。

## この検証で言えること・言えないこと

今回の範囲では、ReferyTaleを明示適用すると、名称より前の外部化、本文語彙の追跡、未確定性の保持がbaselineより安定しました。また、本文を先に書いてしまった題材でも、3回とも元要求からPhase 1を作り直してから本文を再生成しました。

一方、これは7件の人工作成fixtureを各3回実行した結果であり、すべての設計・調査・実装作業へ一般化できる統計的証明ではありません。採点には人の判断が含まれ、固定seedもありません。また、`$referytale` を明示した条件なので、Ruleだけによる自動発火率はこの結果に含まれません。

公開時は、「42回で完全に証明済み」ではなく、次のように表現するのが正確です。

> Codex `gpt-5.6-sol`、reasoning effort `medium` で42回の独立比較を実施しました。ReferyTale適用時は、名称より先にPhase 1を保存する順序を21/21回で守り、厳格な全条件では17/21回が合格しました。4件の不合格と実行証拠も含めて公開しています。
