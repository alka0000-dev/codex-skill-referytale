# 保守モード開始機能 設計書

## 1. 目的

変更承認、利用者セッション、予定開始時刻を確認し、すべての開始前提条件が成立した場合に限って管理サービスへ保守モード開始要求を一度だけ送信する。送信と応答の事実は監査可能な形で保存する。

## 2. 要求回復対応表

先行草稿の表現を、元要求へ次のとおり対応付ける。この表を以後の設計およびテストの基準とする。

| 要求ID | 元要求 | 先行草稿の対応箇所 | 設計要素 | 検証観点 |
|---|---|---|---|---|
| R-01 | 変更承認記録が承認済みである | 「保守移行点を満たしたら」 | `変更承認済み条件` | 未承認・承認待ち・却下では送信しない |
| R-02 | アクティブな利用者セッションが0件である | 「保守移行点を満たしたら」 | `利用者セッション解消条件` | 1件以上なら送信しない |
| R-03 | 予定開始時刻に達している | 「保守移行点を満たしたら」 | `予定開始時刻到達条件` | 現在時刻が予定開始時刻未満なら送信しない |
| R-04 | 三条件をすべて満たした場合だけ開始要求を送る | 「開始処理へ進む」 | `保守モード開始適格判定` | 三条件のANDが真のときだけ送信する |
| R-05 | 送信後、開始済み応答までは同じ要求を再送しない | 「保守移行点の間は再送せず」 | `開始要求送信済み状態`、要求IDによる送信抑止 | 応答待ちの再評価・再起動・タイムアウトでも同じ要求を送らない |
| R-06 | 要求ID、送信時刻、応答結果を監査用に保存する | 「結果を記録する」 | `保守モード開始監査記録` | 三項目が永続化され、要求IDで追跡できる |

## 3. 正式名称

先行草稿の曖昧な語は、次の名称に置き換える。

| 草稿の語 | 正式名称 | 定義 |
|---|---|---|
| 保守移行点 | 保守モード開始適格条件 | 下記三条件の論理積 |
| 保守移行点を満たす | 保守モード開始適格 | 三条件が同一判定時点ですべて真である状態 |
| 開始処理 | 保守モード開始要求送信処理 | 要求記録の確定後、管理サービスへ開始要求を送る処理 |
| 保守移行点の間 | 開始要求送信済み状態 | 要求の送信抑止を確定してから開始済み応答を保存するまでの状態 |
| 結果 | 管理サービス応答結果 | 応答区分、応答受信時刻、および管理サービスの結果コード |

三つの個別条件は次の名称とする。

- `変更承認済み条件`: 対象の変更承認記録の状態が `APPROVED` である。
- `利用者セッション解消条件`: 対象環境のアクティブな利用者セッション数が `0` である。
- `予定開始時刻到達条件`: 判定時刻が予定開始時刻以上である。

`保守モード開始適格条件` は次式で定義する。

```text
変更承認済み条件
AND 利用者セッション解消条件
AND 予定開始時刻到達条件
```

## 4. スコープ

### 対象

- 開始前提条件の判定
- 開始要求の生成と一回限りの送信
- 同一要求の再送抑止
- 管理サービス応答の受付
- 監査記録の永続化

### 対象外

- 変更承認そのもののワークフロー
- 利用者セッションを終了させる処理
- 保守モードの終了処理
- 失敗応答、応答欠落または不明応答に対する自動再送

自動再送は元要求に定義がなく、同一要求の再送禁止とも衝突し得るため実施しない。これらは運用確認の対象とする。

## 5. 状態モデル

保守モード開始単位ごとに、次の状態を永続化する。

| 状態 | 意味 | 許可される次状態 |
|---|---|---|
| `WAITING_PREREQUISITES` | 一つ以上の開始前提条件が未成立 | `READY_TO_SEND` |
| `READY_TO_SEND` | 三条件がすべて成立し、送信準備が可能 | `REQUEST_SENT` |
| `REQUEST_SENT` | 要求IDと送信時刻を確定し、管理サービスへの一回限りの送信を開始した状態。再送禁止 | `STARTED`、`MANUAL_REVIEW_REQUIRED` |
| `STARTED` | 管理サービスの開始済み応答を保存済み | なし |
| `MANUAL_REVIEW_REQUIRED` | 失敗、不明応答または応答欠落を確認。自動再送禁止 | なし（別途定義される運用手続きのみ） |

`READY_TO_SEND` は内部的な短時間の状態である。条件判定から `REQUEST_SENT` の確定までに前提データが変わり得る場合は、送信直前に同一の整合性境界で再判定する。

## 6. 処理設計

### 6.1 適格判定

1. 対象の変更承認記録、アクティブセッション数、予定開始時刻を取得する。
2. 三条件を同一の判定時点で評価する。
3. 一つでも偽または取得不能なら `WAITING_PREREQUISITES` とし、要求を生成・送信しない。
4. すべて真なら `READY_TO_SEND` とする。
5. 送信確定の直前に条件を再評価し、すべて真の場合だけ次へ進む。

時刻比較はサービス共通のUTC時刻で行い、`判定時刻 >= 予定開始時刻` を到達とする。

### 6.2 要求の確定と送信

1. 開始対象ごとの一意キーで排他制御を行う。
2. 当該開始対象に `REQUEST_SENT`、`STARTED` または `MANUAL_REVIEW_REQUIRED` の要求が存在すれば、新しい要求を作らず送信しない。
3. 一意な `request_id` を生成する。
4. `request_id` と `sent_at` を含む監査記録、および状態 `REQUEST_SENT` を永続化する。
5. 永続化した同じ `request_id` を用いて管理サービスへ要求を一度送る。

多重起動を防ぐため、開始対象の一意キーには一意制約を設ける。監査記録の確定前にネットワーク送信してはならない。

`sent_at` は、送信処理が管理サービス向け通信へ要求を引き渡す時刻として定義する。監査記録の永続化と外部通信は単一トランザクションにできないため、永続化後・通信前の障害では、実際の到達有無を確定できない。この場合も再送せず `MANUAL_REVIEW_REQUIRED` とし、監査記録と管理サービス側の状態を照合する。

### 6.3 再送抑止

- `REQUEST_SENT` 以降は、定期評価、イベントの重複、プロセス再起動、通信タイムアウトのいずれでも同じ `request_id` を再送しない。
- 応答を受ける前に送信成否を確定できない場合も再送しない。
- `STARTED` 到達後も当該開始対象について新たな開始要求を送信しない。
- 失敗応答、不明応答または所定時間内に応答がない場合は `MANUAL_REVIEW_REQUIRED` とし、自動再送しない。

この仕様は重複要求を避ける一方、要求が管理サービスへ到達しなかった場合に自動回復しない。運用者は管理サービス側の状態を照合し、別途承認された復旧手続きを使用する。

### 6.4 応答処理

1. `request_id` で送信済み要求を特定する。
2. 応答内容と受信時刻を監査記録へ保存する。
3. 応答が開始済みを示す場合、状態を `STARTED` にする。
4. 失敗または解釈不能な応答の場合、状態を `MANUAL_REVIEW_REQUIRED` にする。
5. 未知の `request_id` の応答は状態を変更せず、孤立応答として監査記録へ保存して警告する。
6. 同一応答を再受信した場合は、既存結果と一致すれば状態を変えず受信事実のみ追記する。不一致なら `MANUAL_REVIEW_REQUIRED` として警告する。

## 7. データ設計

`保守モード開始監査記録` は少なくとも次の項目を持つ。

| 項目 | 必須 | 説明 |
|---|---:|---|
| `request_id` | 必須 | 開始要求を一意に識別するID |
| `maintenance_target_id` | 必須 | 保守モード開始対象の識別子 |
| `state` | 必須 | 状態モデルで定義した現在状態 |
| `sent_at` | 必須（送信時） | 管理サービス向け通信へ要求を引き渡した時刻 |
| `response_result` | 応答後必須 | `STARTED`、`FAILED`、`UNKNOWN` のいずれか |
| `response_code` | 応答後 | 管理サービスが返した結果コード |
| `response_received_at` | 応答後必須 | 応答を受信した時刻 |
| `approval_record_id` | 必須 | 判定に使用した変更承認記録のID |
| `active_session_count` | 必須 | 送信直前の判定で確認した件数（常に0） |
| `scheduled_start_at` | 必須 | 判定に使用した予定開始時刻 |
| `eligibility_checked_at` | 必須 | 三条件を最終確認した時刻 |

元要求で必須とされた監査項目は `request_id`、`sent_at`、`response_result` である。残りは判定根拠と応答追跡性を確保するために保存する。

監査記録は追記または履歴保持方式とし、過去の送信・応答事実を上書き消去しない。アクセスは監査権限を持つ主体に限定する。

## 8. 擬似コード

```text
evaluate_and_start(target):
  facts = load_start_facts(target)
  if not eligible(facts):
    keep WAITING_PREREQUISITES
    return NOT_SENT

  begin transaction with lock(target)
    if terminal_or_sent_record_exists(target):
      commit
      return NOT_SENT

    facts = reload_start_facts(target)
    if not eligible(facts):
      set WAITING_PREREQUISITES
      commit
      return NOT_SENT

    request_id = generate_unique_id()
    sent_at = clock.now_utc()
    persist audit record(request_id, sent_at, facts)
    set REQUEST_SENT
  commit

  send_once_to_management_service(request_id, target)
  return SENT

handle_response(response):
  record = find_by_request_id(response.request_id)
  persist response result and received time
  if response means STARTED:
    set STARTED
  else:
    set MANUAL_REVIEW_REQUIRED
```

## 9. 受け入れテスト

| テストID | 条件 | 期待結果 | 対応要求 |
|---|---|---|---|
| T-01 | 承認済み、セッション0、予定時刻到達 | 要求を1回だけ送信する | R-01〜R-04 |
| T-02 | 承認済み以外、他二条件成立 | 送信しない | R-01、R-04 |
| T-03 | セッション1件以上、他二条件成立 | 送信しない | R-02、R-04 |
| T-04 | 予定時刻前、他二条件成立 | 送信しない | R-03、R-04 |
| T-05 | 三条件の任意の組合せで一つ以上不成立 | 送信しない | R-04 |
| T-06 | `REQUEST_SENT` 中に評価を複数回実行 | 同じ要求も新しい要求も送信しない | R-05 |
| T-07 | `REQUEST_SENT` 中にプロセス再起動 | 再起動後も再送しない | R-05 |
| T-08 | 通信タイムアウト | 自動再送せず、手動確認対象にする | R-05 |
| T-09 | 開始済み応答 | 応答結果を保存し `STARTED` になる | R-05、R-06 |
| T-10 | 失敗または不明応答 | 結果を保存し、再送せず手動確認対象にする | R-05、R-06 |
| T-11 | 送信成功 | 要求IDと送信時刻が監査記録に存在する | R-06 |
| T-12 | 並行して二つの評価処理を実行 | 一意制約により送信は1回だけとなる | R-04、R-05 |

## 10. 先行草稿の改訂文

> 変更承認済み条件、利用者セッション解消条件、および予定開始時刻到達条件を同一判定時点ですべて満たした場合に限り、保守モード開始要求送信処理へ進む。要求IDと送信時刻を永続化して開始要求送信済み状態へ遷移した後は、管理サービスの開始済み応答を保存するまで同一要求を再送しない。管理サービスの応答結果は要求IDに関連付けて監査記録へ保存する。

この改訂文は概要であり、再送抑止や異常応答時の詳細は本設計書の状態モデルおよび処理設計を正とする。
