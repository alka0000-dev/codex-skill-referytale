# 保守モード開始機能 設計書

## 1. 目的

承認済みの変更計画について、利用者への影響がなく予定時刻に達した場合に限り、管理サービスへ保守モード開始要求を一度だけ送信する。送信から管理サービスによる開始確認までの重複送信を防ぎ、送信・応答の証跡を監査可能な形で保存する。

本書は [要求・設計対応表](requirements-traceability.md) の REQ-01〜REQ-06を具体化する。

## 2. スコープ

### 2.1 対象

- 保守開始前提条件の評価
- 管理サービスへの保守モード開始要求の送信
- 送信後の再送抑止
- 要求と応答の監査記録

### 2.2 対象外

- 変更承認そのもののワークフロー
- 利用者セッションを終了させる処理
- 予定開始時刻の登録・変更
- 管理サービスでの保守モード開始処理
- 応答が「開始済み」以外の場合の再実行判断および手動復旧手順
- 監査記録の保存期間および削除方針

## 3. 名称

| 日本語名 | 識別名 | 意味 |
|---|---|---|
| 保守開始前提条件 | `MaintenanceStartPreconditions` | 送信可否を決める三条件の論理積 |
| 保守モード開始要求 | `MaintenanceStartRequest` | 管理サービスへ送る開始要求 |
| 開始要求応答待ち | `START_REQUEST_PENDING` | 要求を一回限り送信する権利を確保してから「開始済み」応答を受けるまでの状態 |
| 保守開始済み | `MAINTENANCE_STARTED` | 管理サービスから「開始済み」応答を受けた状態 |
| 保守開始要求監査記録 | `MaintenanceStartAudit` | 要求ID、送信時刻、応答結果を保持する監査証跡 |

既存草稿の「保守移行点」は使用しない。送信前の条件と送信後の状態を混同するためである。

## 4. 機能要件

### 4.1 保守開始前提条件

対象の変更計画について、次の三条件を同じ評価処理内で確認する。

1. 対応する変更承認記録の状態が `APPROVED` である。（REQ-01）
2. 評価時点のアクティブな利用者セッション数が `0` である。（REQ-02）
3. 評価時刻が予定開始時刻以後である。（REQ-03）

送信可否は次式で決める。

```text
canStartMaintenance =
    approvalStatus == APPROVED
    AND activeUserSessionCount == 0
    AND evaluatedAt >= scheduledStartAt
```

三条件がすべて真の場合だけ送信処理へ進む。偽の条件が一つでもある場合、条件値が取得できない場合、または取得処理が失敗した場合は送信しない。（REQ-04）

条件不成立時は、後続の定期評価または明示的な再評価で三条件を改めて取得する。前回値を送信判断に流用しない。

### 4.2 一回限りの送信権確保

三条件の成立後、対象の変更計画に対して送信権の確保を試みる。次の処理を一つのデータベーストランザクションで行う。

1. 対象の状態が未送信であることを条件付き更新で確認する。
2. UUID形式の一意な `requestId` を生成する。
3. 状態を `START_REQUEST_PENDING` に変更する。
4. 同じ `requestId` を持つ `MaintenanceStartAudit` を作成する。

条件付き更新に成功した一処理だけが送信権を得る。更新件数が0件の場合は、別処理が送信権を取得済み、応答待ち、または開始済みであるため送信しない。これにより、並行実行や重複起動による多重送信を抑止する。

### 4.3 要求送信

送信権を得た処理は、生成した `requestId` と対象の変更計画IDを含む `MaintenanceStartRequest` を管理サービスへ一回送信する。

管理サービスへの送出を開始した時刻をUTCの ISO 8601 形式で `sentAt` に記録する。`sentAt` の保存後、状態が `START_REQUEST_PENDING` である間は、同じ変更計画に対する保守モード開始要求を送信しない。（REQ-05）

### 4.4 応答処理

管理サービスから応答を受けたら、`requestId` で対応する監査記録を特定し、受信した応答結果を `responseResult` に保存する。（REQ-06）

- 応答結果が `STARTED`（開始済み）の場合、対象の状態を `MAINTENANCE_STARTED` に更新する。
- `STARTED` 以外の応答の場合、応答結果は保存するが、状態は `START_REQUEST_PENDING` のままとする。
- 既知の `requestId` と一致しない応答では状態を変更しない。
- 同じ `requestId` の同一応答を複数回受けた場合は冪等に扱う。非開始結果の後に `STARTED` を受けた場合は `responseResult` を `STARTED` に更新する。`STARTED` は終端結果とし、その後に異なる結果を受けても上書きせず監査異常として扱う。

`START_REQUEST_PENDING` は `STARTED` 応答を受けるまで再送禁止を表す。タイムアウト、通信エラー、プロセス停止により送信結果が不明な場合も、自動再送は行わない。重複送信防止を優先し、復旧判断は対象外の手動運用へ委ねる。

## 5. 状態遷移

| 現在状態 | イベント／条件 | 次状態 | 外部送信 |
|---|---|---|---|
| `NOT_REQUESTED` | 三条件のいずれかが偽または不明 | `NOT_REQUESTED` | なし |
| `NOT_REQUESTED` | 三条件がすべて真、送信権確保に成功 | `START_REQUEST_PENDING` | 一回だけ送信 |
| `NOT_REQUESTED` | 三条件がすべて真、送信権確保に失敗 | 実格納状態を維持 | なし |
| `START_REQUEST_PENDING` | 再評価、重複起動、タイムアウト、通信エラー | `START_REQUEST_PENDING` | なし |
| `START_REQUEST_PENDING` | `STARTED` 以外の応答 | `START_REQUEST_PENDING` | なし |
| `START_REQUEST_PENDING` | `STARTED` 応答 | `MAINTENANCE_STARTED` | なし |
| `MAINTENANCE_STARTED` | 任意の再評価 | `MAINTENANCE_STARTED` | なし |

## 6. 処理フロー

```text
開始契機
  │
  ├─ 変更承認状態を取得 ─ 取得失敗／APPROVED以外 ─→ 終了（送信なし）
  ├─ アクティブセッション数を取得 ─ 取得失敗／0以外 → 終了（送信なし）
  ├─ 予定開始時刻を評価 ─ 取得失敗／到達前 ───────→ 終了（送信なし）
  │
  ├─ 送信権を条件付きで確保 ─ 失敗 ────────────→ 終了（送信なし）
  ├─ 要求ID・監査記録を永続化
  ├─ sentAtを記録して管理サービスへ一回送信
  └─ 応答受信
       ├─ STARTED ─→ 応答結果を保存し、MAINTENANCE_STARTEDへ遷移
       └─ その他 ──→ 応答結果を保存し、START_REQUEST_PENDINGを維持
```

## 7. データ設計

### 7.1 保守開始制御

| 項目 | 型・制約 | 説明 |
|---|---|---|
| `changePlanId` | ID、主キーまたは一意 | 対象の変更計画 |
| `status` | 列挙、NOT NULL | `NOT_REQUESTED`、`START_REQUEST_PENDING`、`MAINTENANCE_STARTED` |
| `requestId` | UUID、NULL可、一意 | 送信権確保時に設定 |
| `updatedAt` | UTC日時、NOT NULL | 状態の最終更新時刻 |

`changePlanId` の一意制約と、`requestId` の一意制約を設ける。

### 7.2 MaintenanceStartAudit

| 項目 | 型・制約 | 設定時点 | 説明 |
|---|---|---|---|
| `requestId` | UUID、主キー | 送信権確保時 | 要求と応答を関連付ける一意なID |
| `changePlanId` | ID、NOT NULL | 送信権確保時 | 対象の変更計画 |
| `sentAt` | UTC日時、NULL可 | 送出開始時 | 要求送信時刻。未送出ならNULL |
| `responseResult` | 列挙または文字列、NULL可 | 応答受信時 | 最後に受け入れた管理サービスの応答結果。未応答ならNULL、`STARTED` は終端値 |
| `responseReceivedAt` | UTC日時、NULL可 | 応答受信時 | 応答受信時刻。監査補助項目 |

監査記録は業務データと分離し、通常の状態更新によって削除しない。保存期間とアクセス制御は別途定める。

## 8. 整合性と障害時の扱い

- 送信権確保と監査記録作成は同一トランザクションで確定し、片方だけが残る状態を作らない。
- 外部送信とデータベース更新は単一トランザクションにできないため、送信結果が不明な障害が起こり得る。その場合も `START_REQUEST_PENDING` を維持し、自動再送しない。
- `sentAt` の書き込み失敗時は外部送信へ進まない。状態は `START_REQUEST_PENDING` のまま保持し、手動確認対象とする。
- 応答結果の保存と `MAINTENANCE_STARTED` への遷移は同一トランザクションで行う。
- 前提条件を満たさない、または評価できないことは失敗閉鎖（fail closed）として扱い、外部要求を送らない。

## 9. 監査要件

監査では最低限、次の関連を追跡できること。

- どの変更計画に対する要求か：`changePlanId`
- どの要求か：`requestId`
- いつ送信したか：`sentAt`
- 管理サービスが何を返したか：`responseResult`

未送信または未応答は、対応項目がNULLであることにより区別する。監査記録の更新主体を本機能に限定し、更新履歴または改ざん防止の方式はシステム共通の監査基盤に従う。

## 10. 受け入れ試験

| 試験ID | 対応要求 | 条件・操作 | 期待結果 |
|---|---|---|---|
| AT-01 | REQ-01〜04 | 三条件の真偽8組を評価する | すべて真の1組だけが送信権確保へ進む |
| AT-02 | REQ-01〜04 | 各条件の取得を個別に失敗させる | いずれも要求を送信しない |
| AT-03 | REQ-05 | 同じ変更計画を複数処理から同時評価する | 一処理だけが送信権を得て、送信は一回だけとなる |
| AT-04 | REQ-05 | 送信後、応答前に再評価する | 要求を再送しない |
| AT-05 | REQ-05 | 送信タイムアウトまたは通信結果不明を発生させる | `START_REQUEST_PENDING` を維持し、自動再送しない |
| AT-06 | REQ-05〜06 | `STARTED` 応答を返す | 応答結果を保存し、`MAINTENANCE_STARTED` へ遷移する |
| AT-07 | REQ-05〜06 | `STARTED` 以外の応答を返す | 応答結果を保存し、`START_REQUEST_PENDING` を維持して再送しない |
| AT-08 | REQ-06 | 正常な送信と応答を完了する | 要求ID、送信時刻、応答結果を監査記録から参照できる |
| AT-09 | REQ-05〜06 | 同一応答を複数回受信する | 状態と監査結果が破損せず、重複送信も発生しない |
| AT-10 | REQ-06 | 未知の要求IDを持つ応答を受信する | 既存状態・監査記録を変更しない |

## 11. 設計前提・要確認事項

以下は元要求だけでは確定しないため、実装着手前に接続先またはシステム共通仕様との整合を確認する。

- 「アクティブな利用者セッション」の判定元、対象範囲、集計時点
- 変更承認記録、セッション数、予定開始時刻を取得する各インターフェース
- システム標準時刻源と時刻同期方式
- 管理サービスの要求・応答スキーマ、`requestId` の返却方法、`STARTED` の正式な応答値
- 条件再評価の開始契機と間隔
- 通信結果不明または `STARTED` 以外の応答に対する手動復旧手順
- 監査記録の保存期間、閲覧権限、改ざん防止方式

これらが未確定でも、三条件の論理積、応答待ち中の再送禁止、監査必須三項目という本書の要求境界は変更しない。

## 12. 改訂した要約文

> 変更承認済み、アクティブな利用者セッション0件、予定開始時刻到達の三条件をすべて満たした場合だけ、一意な要求IDを付けて管理サービスへ保守モード開始要求を一回送信する。送信後は「開始済み」応答を受けるまで開始要求応答待ちとして再送を禁止し、要求ID、送信時刻および応答結果を保守開始要求監査記録に保存する。
